# 非追不可匯入檔

首頁「非追不可匯入檔」→ 選日期 → 收貨 → 製造 → 交貨。
每一步先核對數量與平台自編碼，勾選確認後下載 XLS，交給平台的「資料匯入」。
不會自動上傳、建立或刪除平台申報紀錄。

## 資料來源與範圍

- 收貨：未取消的採購品項，以送達日優先，未指定時採用供餐日；只有以 g 為基本單位的 snapshot 才自動換算公斤。個數類請補實際重量。
- 製造／交貨：當日有供餐、正數人數的學校菜單，彙整葷素與原料；餐別分開。原料採用菜單的本次配方覆寫，而非只讀共享配方。
- 小便當併入平鎮高中；新勢幼、信義幼併入各自國小。明原、中央大學幼兒園、廣豐依使用者指定排除。
- 產品碼、下游業者碼與已確認份重由私有服務設定 `FTRACE_PRODUCTS_JSON` 載入；不放入公開程式碼。未設定或設定無效時留空，必須補齊才可匯出。無已確認份重時保持空白。
- 交貨第一次載入時沿用已暫存的當日製造份數與重量，仍可改為實際交貨值。

## 編碼對照與草稿

原料名稱不等於平台自編碼，供應商碼也不等於原料規格碼。缺值時不得匯出。
系統使用私有 `FTRACE_REFERENCES_JSON` 對照，預填原料、唯一規格與供應商編碼，仍可逐項編輯，不需每個瀏覽器匯入。也可在「平台編碼對照」補充 JSON：

```json
{
  "materials": [{"name": "食材名稱", "code": "平台原料碼", "specs": [{"code": "平台原料規格碼", "supplier_name": "廠商名稱"}]}],
  "products": [{"name": "學校完整名稱", "code": "產品碼", "grams": 600}],
  "parties": [{"name": "供應商或學校完整名稱", "code": "交易對象碼"}]
}
```

交易對象主檔另存於受限存取的 Supabase `kitchen_ftrace_party`，以平台交易對象自編碼為主鍵；不將客戶寫入供餐學校，也不將全名相同但編碼不同的對象任意合併。資料表只向匯出頁提供名稱、編碼、角色及已核對別名，不提供地址或聯絡人。收貨只比對供應商角色，交貨只自動帶入客戶角色；人工填寫值與原有私有設定優先保留。交易對象名單更新時只補不存在的編碼，不覆蓋既有編碼。原料、規格、產品其他資料仍由私有設定提供。

名稱只做空白正規化後的唯一完全比對，不做模糊配對。多個規格碼需人工確認。
對照項目可附 `aliases` 字串陣列，只有已核對的別名才自動帶入；不從製造商名稱推測實際供應商。多規格中只有一項與採購廠商名稱相符時可帶入，否則留空。
規格選項依當列原材料過濾，括號顯示 `product_name`、`package_label`、`manufacturer_name` 與廠商名稱；選定後欄位下方仍顯示說明。變更原材料會清除先前規格，避免跨食材誤選。說明取自平台主檔，未提供的廠牌或包裝資訊不猜測。
每份成品重量隨當日草稿帶到前端；舊草稿重量空白時，會依已確認份重與還原後的份數重新預填製造／交貨公斤數。已有人工填寫的重量保留，未設定份重者顯示補填原因。
較大的服務設定可使用 `FTRACE_REFERENCES_ZLIB_BASE64`（UTF-8 JSON → zlib → base64），仍只放 Render 私有設定，不提交業務對照到 GitHub。頁面僅提供名稱、編碼、規格和已確認別名，不帶出私有設定的其他欄位，且禁用頁面快取。
服務設定格式為 JSON 陣列，例如 `[{"name":"學校完整名稱","code":"TEST-P","customer_code":"TEST-C","grams":600}]`。名稱須使用合併後的學校名稱；產品碼與下游碼分開核對，不假設相同。只更新這個環境變數，不替換既有服務設定。
對照與按日期／類型區分的草稿存於同一瀏覽器 localStorage，可備份 JSON。
這些草稿不是共用的正式收貨／出餐實績；清除瀏覽資料會移除暫存。
重新載入草稿時只保留目前來源仍存在的項目，新增或刪除來源後須再次核對。

## 官方格式

欄位與工作表取自 2026-11-05 從平台下載的官方 ZIP：

- `https://ftraceindustry.fda.gov.tw/Document/收貨資料.zip`：餐盒業收貨資料（非依批號）
- `https://ftraceindustry.fda.gov.tw/Document/製造資料.zip`：餐盒業製造資料（非依批號）
- `https://ftraceindustry.fda.gov.tw/Document/交貨資料.zip`：餐盒業交貨資料（非依批號）

schema 固定於 `data/ftrace/schemas.json`；保留未使用的工作表及欄位標題，所有資料格使用文字格式。平台 24.14 版實際要求製造原料表名為「製造餐食原材料」，下載的舊範本「製造餐盒原材料」會被拒絕；依平台實際驗證結果修正。
每日申報方式為 `2`，日期 `YYYY/MM/DD`，流水號 `01` 起；最多 99 筆主資料。
這是平台一般「資料匯入」用的餐食製造業格式，非批號追溯格式，也不產生虛構批號。
交貨預設直接交給下游業者，無另行物流業者、自用或直接販售消費者。
若實際物流或交貨方式不同，須擴充表單後再匯出。

## 隔離與驗證

只有 `app.py` 增加一個模組匯入、首頁增加一個入口；既有計算程式未修改。
新服務只 SELECT，不建立資料表、不更新菜單／採購，不改 Supabase schema。
POST 沿用團膳 CSRF 保護，伺服器驗證必填欄位、日期、正數、精度與人工確認。
下載回應禁用快取。測試含完整回歸、實際瀏覽器三步驟下載和 XLS 讀回。
以平台實際匯入結果驗證相容性；僅本機可讀取不代表平台可接受。舊式 BIFF8 XLS 為必要格式，不能將 XLSX 改副檔名代替。

### 目前相容性驗證狀態

平台拒絕 XLSX；只有 Workbook stream 的 xlwt XLS 亦出現「External table is not in the expected format」。同內容經 LibreOffice 存成 Excel 97 XLS 後，收貨匯入顯示「處理完成」，並查到新增的 0.2 公斤毛豆仁測試紀錄。

補上 OLE 識別資訊後平台仍拒絕。最終定位到 xlwt 1.3 的 WriteAccess 紀錄：BIFF8 要求 XLUnicodeString，套件卻寫成舊式定長字串。`services/ftrace_xls.py` 依 [MS-XLS 2.4.349](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/231de348-d93c-4be3-a12b-a19173a45d69) 修正成無使用者名稱的合法字串，保持其他 BIFF 紀錄與資料內容不變；同時補上通用 OLE 識別資訊。伺服器不依賴 LibreOffice，識別資訊不含業務資料。

2026-11-05 已用實際叫貨／菜單來源的樣本，在平台確認三類「處理完成」且清單查到新增紀錄。公開文件只記錄驗證時間，不包含業務編碼與申報內容：

- 收貨 `verified_receiving.xls`：19:08:06 完成。
- 製造 `final_manufacture.xls`：19:13:36 完成。
- 交貨 `verified_delivery.xls`：19:11:48 完成。

另有較早的 LibreOffice 收貨測試。使用者確認後，四筆測試申報均已刪除，筆數恢復為收貨 135、製造 163、交貨 121；原有資料保留。失敗匯入僅留下上傳紀錄，未新增申報資料。

## 依批號申報（新增）

頁面預設勾選「依批號申報」，可取消以保留原非批號格式。舊草稿的編碼、份數、重量保留；切換模式不修改菜單、採購或平台資料。

- `batch_schemas.json` 直接取自官方 ZIP 的「收貨資料(依批號)」「餐食製造(依批號)」「交貨資料(依批號)」範本，保留所有空工作表與標題。`services/ftrace_batch.py` 獨立驗證，不改原匯出分支。
- 收貨填實際批號、流水號與實收重量；原料製造日、有效日選填。內部批號依既有慣例預填原材料自編碼＋民國收貨日期；如包裝已有原廠批號或平台已有申報，應改用該原紀錄。可按按鈕依目前原料碼／日期重新帶入。日申報日期須等於實際收貨日期；沒有驗收功能，採購預填仍須人工核實。
- 製造批號預填產品自編碼＋民國製造日期，製造日、有效日先帶供餐日期，必須依實際生產與保存期限核對；批號可修改。原料用量按菜單本次配方與實際人數估算，個數類不當作重量。
- 每一原料可拆多批，從同瀏覽器跨日期已暫存收貨選取，或手動補平台既有原料批次。新制以收貨批號對應，舊制以收貨日期對應，兩者擇一。收貨申報年月／日期及流水號須與平台相同。
- 交貨初次帶入已暫存製造批號、日期與數量，另提供明確的重新帶入按鈕。若已有當日製造暫存，下載前檢查批號／日期一致及交貨不得大於該暫存製造量。
- 日期、正數、精度、缺批次、同批重複選取、單次及本次所選學校合計使用量超過已知收貨重量均會檢查。手動補批次沒有庫存容量時不能驗證存量。

批次草稿仍存瀏覽器 localStorage，並非共用庫存帳，也不自動查詢平台是否已申報。沒有跨日期已用量扣庫存，不可將暫存批次視為已申報或尚有庫存。不同裝置要核對／移轉草稿後使用。既有平台紀錄不會被此功能覆寫或刪除。

新增批號回歸測試：160 passed、3 skipped；含 BIFF8 XLS 讀回、三類欄位串接、跨月舊庫存、多批使用、不合法日期／重量與不寫入原資料的驗證。

### 批號平台驗證

2026-11-06 以程式直接產生的 BIFF8 XLS 在非追不可 24.14 完成驗證：收貨 01:03:48、製造 01:06:39、交貨 01:07:59 均顯示「處理完成」。製造清單顯示依批號勾選與批號；交貨明細指向同一製造批號及日期，製造清單的交貨重量同步增加。原料來源使用剛匯入收貨批次。公開文件不包含業務編碼與內容。

使用者確認後，這次三筆批號測試紀錄按交貨→製造→收貨順序刪除，平台筆數恢復為收貨 135、製造 163、交貨 121。原有申報保留。

歷史批號慣例已由平台原紀錄核對：原材料／產品自編碼＋民國年月日（非供應商碼）。新增測試確認格式、缺碼不猜、長度不截斷；完整回歸 161 passed、3 skipped。已有手填批號保留，交貨沿用製造批號。

## 共用紀錄與歷史收貨

「共用資料區」保存歷史收貨 XLS 的原檔、每個原始列、廠商／供應商對照及核對紀錄。
支援餐盒業 v1.2 舊版與依批號收貨；依欄位名稱讀取，流水號 `0` 保留為 `0`。
缺批號或收貨日期不猜填。只有使用者勾選「日申報日期就是實際收貨日」時，才以申報日期補空白，並保存日期依據。
同檔依 SHA-256 去重；跨檔相同收貨識別不累加重量。識別重複而有不同重量或未核對的列，禁止自動帶入。
若舊版匯出未包含平台原本的新制批號，須在「核對／補齊」填入原批號，不能自行重編。

三類編輯頁按「儲存到共用資料區」後，可跨電腦接續編輯；每次修改新增版本。
以載入版本做樂觀鎖，另一個人先儲存時回傳 409，不覆蓋共用紀錄。舊瀏覽器暫存可移入，已存在的共用紀錄不覆蓋。
交貨優先帶入同日共用製造資料；平台匯入成功後才由使用者標記申報完成。
已標記完成的紀錄必須在資料區建立修訂草稿才能再儲存，原申報版本保留。

正式與具名練習帳號分別使用原有的資料庫／schema 路由；新增四張表不寫入菜單、採購或其他舊資料。
新增表啟用 RLS 並撤銷 anon/authenticated/PUBLIC 存取，由既有 Flask 後端的資料庫連線使用。
尚未實作期初庫存、跨日耗用扣帳或平台自動回讀；收貨量不是剩餘庫存，儲存／下載不是平台申報成功。
